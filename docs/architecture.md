# Architecture

Switchboard is a TypeScript monorepo (npm workspaces): one Next.js app and a
handful of small packages. Postgres is the only service, and the job queue lives
in it too.

```
apps/web                Next.js app: hosted forms, booking, admin, API routes
  server.mjs            HTTP wrapper: real client address, config check, then Next
  src/lib               server logic (routes stay thin and call into here)
packages/core           pure logic: rules engine, form validation, slots, rotation
packages/config         switchboard.yaml: load, validate, apply (+ CLI)
packages/db             Drizzle schema, SQL migrations, migrate script
packages/calendar-google  Google OAuth, free/busy, events (plain fetch)
packages/crm-hubspot    HubSpot OAuth, contacts, owners, meetings (plain fetch)
packages/embed          the embed loader (minified into apps/web/public)
packages/ui             design tokens (CSS custom properties)
```

`packages/core` has no I/O: everything that touches the database or the
network lives in `apps/web/src/lib` or the provider packages, so the logic
that decides where a lead goes is tested as plain functions.

## A lead, end to end

1. **Submit** (`api/f/[slug]/submit` → `lib/submit.ts`). Validate against the
   form's fields, reject disposable addresses, return early on an idempotent
   retry.
2. **Look up the CRM** (`lib/crm.ts`), but only for the `crm.*` paths the rule
   set actually reads, within a 3-second budget. An outage means "no CRM
   data", not a failed submit.
3. **Evaluate** (`core/rules/evaluate.ts`) against `{ form, crm }` inputs
   built by `buildRuleInputs` (which adds `form.email_domain`). First match
   wins; the trace records why each rule did or didn't match.
4. **Pick a rep** (`lib/routing.ts` + `core/strategies/select-rep.ts`). For
   team routes, the app locks the team's memberships `FOR UPDATE`, reads the
   rotation credit, picks the rep, and writes the new credit, so concurrent
   leads take turns.
5. **Record** the submission and decision in one transaction.
6. **Queue side effects** (`lib/jobs.ts`): the CRM contact write-back and a
   delayed speed-to-lead alert.
7. **Book** (`api/bookings` → `lib/bookings.ts`). Check the rep is the routed
   one and the time is an offered slot, claim it with a `hold` row (the
   `bookings_no_overlap` exclusion constraint rejects overlaps atomically),
   re-check the rep's live free/busy, create the event with a deterministic
   id (retries can't double-invite), confirm, and queue the confirmation
   email and CRM meeting log.

## Data model

| Table | Holds |
| --- | --- |
| `orgs` | The org (one per instance) |
| `users` | Reps: email (unique, case-insensitive), time zone, working hours |
| `teams`, `team_members` | Teams; weight, weekly capacity, active flag, rotation credit |
| `rule_sets` | Versioned rule JSON; identical content reuses a version |
| `forms` | Fields, settings (submit label, self-serve URL), rule set |
| `submissions` | Lead answers; idempotent per form + key; send-once markers |
| `routing_decisions` | Inputs, matched rule, outcome, latency |
| `bookings` | Hold/confirmed/cancelled; calendar event, Meet link, CRM meeting |
| `integrations` | Encrypted OAuth tokens: org-wide (HubSpot) or per rep (Google) |

Deleting a submission cascades to its decisions and bookings (data erasure).
Migrations are generated from `packages/db/src/schema.ts` with
`npm run db:generate` and committed as SQL; hand-written additions (the
exclusion constraint, data fixes) are appended to the generated file.

## Background jobs

`pg-boss` runs in the web process (`lib/queue.ts`, `lib/jobs.ts`): no Redis,
no separate worker. Jobs retry with exponential backoff, and each handler is
idempotent (`crm_synced_at`, `confirmation_sent_at`, `crm_meeting_id`,
`alerted_at`), so a retry never sends twice. If the queue can't start,
immediate jobs run inline instead.

## Security model

- **Leads** are anonymous. Their submission id, which only the
  browser that submitted receives, authorizes them to see their routed rep's open
  times and book that rep, nothing else.
- **Reps** never sign in. They connect a calendar through a signed,
  expiring link generated by the admin.
- **The admin** signs in with credentials from the environment (Auth.js JWT
  sessions; changing the password ends existing sessions).
- Secrets: `AUTH_SECRET` signs sessions, OAuth state, and emailed links;
  `TOKEN_ENCRYPTION_KEY` encrypts OAuth tokens (AES-256-GCM).
- `server.mjs` resolves the client address from the socket and
  `TRUSTED_PROXY_HOPS`, so rate limits can't be dodged with a forged
  `X-Forwarded-For`.

## Adding a calendar or CRM provider

The provider packages are deliberately thin `fetch` clients; the app owns
tokens and orchestration. To add, say, Outlook:

1. **Client package** (`packages/calendar-outlook`): OAuth URL / code
   exchange / refresh, free/busy for a time range, and event creation with an
   idempotent id. Mirror `packages/calendar-google` and its tests; raise typed
   errors that carry the HTTP status.
2. **Schema**: add the provider to `integrations.provider`
   (`packages/db/src/schema.ts`) and generate a migration.
3. **Token storage** is generic (`lib/token-store.ts`): store per rep with
   `{ orgId, userId }`.
4. **Wiring**: connect/callback routes like `api/integrations/google/*`, and
   in `lib/integrations.ts` (availability) and `lib/bookings.ts`
   (`reserveCalendar`) pick the client for the rep's connected provider.
5. **Admin**: show the connection on `/integrations`.

A CRM follows the same pattern with `packages/crm-hubspot` and `lib/crm.ts`;
`fetchCrmContext` must return the same `{ contact: { id, owner } }` shape so
existing rules keep working.

## Testing

| Suite | Command | What it covers |
| --- | --- | --- |
| Unit | `npm test` | Pure logic, provider clients (mocked fetch), helpers |
| Postgres | `npm run test:db` (needs `TEST_DATABASE_URL`) | Constraints, transactions, rotation under concurrency, booking rules, erasure |
| Browser | `npm run test:e2e` | The lead flow on a production build, desktop and mobile |

CI runs all three on every pull request, plus a Docker build.
