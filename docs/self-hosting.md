# Self-hosting Switchboard

Everything you need to run Switchboard on your own infrastructure.

## Requirements

- **Docker** (recommended), or Node.js 22 with **Postgres 16+**.
- ~512 MB RAM for the app, plus Postgres.
- Outbound HTTPS to Google, HubSpot, Slack, and your SMTP provider. The only
  inbound port is the app's.

## Quick start

```bash
git clone https://github.com/Preetish/switchboard && cd switchboard
mkdir -p config && cp switchboard.example.yaml config/switchboard.yaml   # then edit it
docker compose up -d
docker compose logs app | grep "Admin login"
```

On first start the container:

1. generates `AUTH_SECRET`, `TOKEN_ENCRYPTION_KEY`, and an admin password
   (unless you set them) and keeps them in the `appdata` volume, printing
   the password once;
2. applies database migrations;
3. applies `config/switchboard.yaml` (or loads the demo when there is no
   file and `SEED_DEMO_DATA=true`, the compose default);
4. starts the app on port 3000 with a healthcheck at `/api/health`.

Compose uses the published image `ghcr.io/preetish/switchboard` when it
exists and builds from your checkout otherwise. Pin a version with
`SWITCHBOARD_VERSION=0.1.0`.

Postgres is not published on the host. For local development,
`docker-compose.dev.yml` publishes it on `127.0.0.1:5432` (see
[CONTRIBUTING.md](../CONTRIBUTING.md)).

## Configuration reference

Your reps, teams, forms, and rules go in `switchboard.yaml` (see
[configuration.md](configuration.md)). Everything else is an environment
variable (compose reads `.env`; see [`.env.example`](../.env.example)).

In production the app **refuses to start** on a missing, malformed, or
known-default secret, and lists what to fix.

| Variable | Required | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | yes | Postgres connection string (compose sets it) |
| `ADMIN_EMAIL` | yes | The admin login (compose default `admin@example.com`) |
| `ADMIN_PASSWORD` | yes | At least 12 characters. Generated by the container if unset. Changing it signs out existing sessions |
| `AUTH_SECRET` | yes | Signs sessions and links, at least 32 characters (`openssl rand -hex 32`). Generated if unset |
| `TOKEN_ENCRYPTION_KEY` | with Google/HubSpot | 64 hex characters; encrypts OAuth tokens at rest (AES-256-GCM). Generated if unset |
| `APP_BASE_URL` | behind a proxy | The public URL, e.g. `https://switchboard.acme.com`. Used in OAuth redirect URIs and emailed links |
| `TRUSTED_PROXY_HOPS` | behind a proxy | How many proxies you run in front (see [HTTPS](#https-and-reverse-proxies)). Default `0` |
| `SWITCHBOARD_CONFIG` | no | Path to the config file (default `/app/config/switchboard.yaml` in Docker) |
| `SEED_DEMO_DATA` | no | Load the demo when there's no config file (compose default `true`) |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | for calendars | Your Google OAuth client ([setup](#google-calendar)) |
| `HUBSPOT_CLIENT_ID` / `HUBSPOT_CLIENT_SECRET` | for CRM | Your HubSpot app ([setup](#hubspot)) |
| `SMTP_URL` / `SMTP_FROM` | for email | `smtps://user:pass@smtp.example.com:465`; confirmations, alerts, deletion links |
| `SLACK_WEBHOOK_URL` | no | Speed-to-lead alerts to Slack (email is the fallback) |
| `SPEED_TO_LEAD_MINUTES` | no | Alert a rep when a routed lead hasn't booked after this many minutes (default 5) |
| `FALLBACK_BOOKING_URL` | no | Booking link included in confirmations when the calendar event couldn't be created |
| `EMBED_ALLOWED_ORIGINS` | no | Space-separated origins allowed to embed forms, e.g. `https://acme.com https://www.acme.com`. Default: any site |
| `TURNSTILE_SITE_KEY` / `TURNSTILE_SECRET_KEY` | no | Turn on a Cloudflare Turnstile check on forms |
| `ADMIN_SETUP_KEY` | no | Bearer token for scripted CSV exports ([API](api.md#export-the-routing-log)) |
| `ORG_SLUG` | no | Pick the org when a database holds several |
| `LOG_FORMAT` | no | `json` forces JSON logs outside production (production always logs JSON) |

## Google Calendar

Each rep connects **their own** calendar: availability comes from their
free/busy, and bookings land on their calendar with a Meet link. Switchboard
doesn't ship a shared OAuth client (Google requires verification for calendar
scopes), so you register your own. It's free and takes about ten minutes.

1. In the [Google Cloud Console](https://console.cloud.google.com/), create or
   pick a project and enable the **Google Calendar API**.
2. **OAuth consent screen:** choose **Internal** if you use Google Workspace
   (no verification needed). Otherwise choose **External** and add your reps
   as test users while in Testing mode. Add the scopes `openid`, `email`,
   `.../auth/calendar.freebusy`, and `.../auth/calendar.events`.
3. **Credentials → Create OAuth client ID → Web application**, with the
   authorized redirect URI `<APP_BASE_URL>/api/integrations/google/callback`.
4. Set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`, then restart.
5. At **/integrations**, use **Copy connect link** next to each rep and send
   it to them. The link is signed, works for 7 days, and only connects
   that rep. If the rep is at your computer, **Connect here** does the same.

Until a rep connects, their working hours and existing Switchboard bookings
decide what's offered. If someone connects the wrong Google account,
/integrations flags it; if access is later revoked, it asks for a reconnect.

## HubSpot

1. Create an app in a [HubSpot developer account](https://developers.hubspot.com/)
   (a public app; private apps can't do the OAuth flow).
2. Redirect URL: `<APP_BASE_URL>/api/integrations/hubspot/callback`.
3. Scopes: `crm.objects.contacts.read`, `crm.objects.contacts.write`,
   `crm.objects.owners.read`.
4. Set `HUBSPOT_CLIENT_ID` / `HUBSPOT_CLIENT_SECRET`, restart, and connect at
   **/integrations**.

Reps are matched to HubSpot owners by email. With HubSpot connected,
`crm.contact.owner` rules work, new leads become contacts, and booked
meetings are logged on the contact's timeline under the rep who took them.

## Email and Slack

- **SMTP** (`SMTP_URL`, `SMTP_FROM`) sends lead confirmations, speed-to-lead
  alerts by email, and data-deletion links. Any provider works (Postmark,
  SES, Mailgun, …). Without SMTP, leads can't self-serve deletion requests;
  you can still erase a lead from the routing log.
- **Slack** (`SLACK_WEBHOOK_URL`, an
  [incoming webhook](https://api.slack.com/messaging/webhooks)) receives
  speed-to-lead alerts; email is the fallback.

Emails, CRM write-backs, and alerts run on a Postgres-backed job queue with
retries, so a provider outage delays them instead of losing them.

## HTTPS and reverse proxies

Terminate TLS at a proxy (Caddy, nginx, Traefik, a cloud load balancer) and
forward to the app. Then set:

```bash
APP_BASE_URL=https://switchboard.acme.com
TRUSTED_PROXY_HOPS=1     # one proxy in front; Cloudflare + nginx would be 2
```

Rate limits key on the client address. The app trusts `X-Forwarded-For` only
for as many hops as `TRUSTED_PROXY_HOPS`, so clients can't fake their
address. The setting must match your setup: too low and everyone shares the
proxy's address; too high and clients can spoof theirs.

A minimal Caddyfile:

```
switchboard.acme.com {
  reverse_proxy localhost:3000
}
```

## Database

- Any Postgres 16+ works. Point `DATABASE_URL` at a managed instance (Neon,
  RDS, Supabase) instead of the compose `db` service if you prefer. The
  `btree_gist` extension must be available (it is on all of those); the
  migrations enable it.
- Migrations are plain SQL in `packages/db/migrations` and run on every
  container start; already-applied ones are skipped.
- Back up with `pg_dump`. Postgres holds all state: config, decisions,
  bookings, and encrypted tokens. The `appdata` volume holds the generated secrets;
  back it up too, or set the secrets yourself.

## Upgrading

```bash
git pull
docker compose pull      # or: docker compose build
docker compose up -d
```

Read the [changelog](../CHANGELOG.md) first. It lists anything that needs
action (for example, reconnecting calendars).

## Without Docker

```bash
npm ci
cp .env.example .env               # fill in DATABASE_URL and the admin settings;
                                   # the server and scripts all read it
npm run db:migrate
npm run config:apply -- switchboard.yaml
npm run build
npm start -w @switchboard/web      # serves on PORT (default 3000)
```

## Security checklist

- [ ] Served over HTTPS, with `APP_BASE_URL` and `TRUSTED_PROXY_HOPS` set.
- [ ] Secrets set by you or generated by the container, never copied from the examples.
- [ ] `SEED_DEMO_DATA=false` or a real `config/switchboard.yaml` in place.
- [ ] `EMBED_ALLOWED_ORIGINS` set to your own site(s).
- [ ] The `appdata` volume and Postgres are backed up.
- [ ] Postgres isn't reachable from the internet.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| Container exits with "will not start until its configuration is fixed" | The listed variables are missing or unsafe; set them in `.env` |
| Container exits after "applying /app/config/switchboard.yaml" | The file doesn't validate; the log lists each problem |
| Google says `redirect_uri_mismatch` | The redirect URI in Google Cloud must be exactly `<APP_BASE_URL>/api/integrations/google/callback` |
| "Calendar access was only partly granted" | The rep unticked a calendar permission; open the connect link again and keep both ticked |
| Every lead hits "Too many submissions" | `TRUSTED_PROXY_HOPS` is 0 behind a proxy, so all leads share its address |
| No speed-to-lead alerts | Neither `SLACK_WEBHOOK_URL` nor `SMTP_URL` is set (the skip is logged) |
| A rep shows no open times | Check their working hours and time zone in the config, and their calendar connection at /integrations |
| Leads go to the fallback queue | The routing log shows why. Usually a team is paused or its reps are at weekly capacity |
